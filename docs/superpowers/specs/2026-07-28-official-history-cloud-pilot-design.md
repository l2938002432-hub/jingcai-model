# 官方历史竞彩验证与国内云端试点设计

## 决策与目标

本阶段将项目从“只验证足球概率”的 `PAPER_ONLY` 原型，升级为可用真实中国竞彩历史赛果和固定奖金进行时间点回测、可自动结算、可在国内云端试点运行的研究系统。

**唯一业务目标是在预先声明的风险约束下最大化可验证的长期净利润。** 系统只在有可复现的正期望、可承受回撤和独立样本证据时给出候选；宁可当天没有推荐，也不为了有单而牺牲长期收益。该目标不等于对某一场、某一日或任意未来周期作出必然盈利承诺，也不包含自动投注、代购、收款或提供博彩服务。

## 范围与分期

本设计拆为四个有明确止损点的里程碑；后续里程碑不得在前一项失败时继续堆叠复杂模型。

1. **官方历史审计**：下载、留档和核验 2023 年起的官方赛果与五玩法奖金变更历史。
2. **时间点回测**：按可见奖金历史重放赛前决策，比较模型、官方市场基线和真实奖金结算。
3. **国内云端探针**：在私有 Gitee Go 仓库验证国内节点对官方接口与通知通道的可用性，不迁移生产任务。
4. **产品闭环**：仅将通过验收的玩法写入候选页、飞书/微信提醒、自动结算与历史复盘。

当前实施只完成第 1、3 项的可运行基础，以及第 2 项的接口和测试骨架；不得在数据审计前产生任何“盈利已验证”的结果。

## 数据边界

### 官方数据

数据提供器以比赛 `matchId` 关联：

- 历史赛果：`getUniformMatchResultV1.qry`；
- 固定奖金历史：`getFixedBonusV1.qry`；
- 赛前伤停：`getInjurySuspensionV1.qry`。

所有原始响应以追加方式保存，写入抓取时间、内容哈希、请求参数和来源标识。不得公开再分发原始响应。访问采用低频、缓存、指数退避和断路器；遇到接口异常、字段变化、过期数据或无法确认许可时，停止候选生成并允许人工导入替代。

伤停空列表只表示“该接口未列出”，不得写成“确认无人伤停”。首发不属于硬依赖；只有在该信息的公开时间早于决策时间且仍可投注时才可作为特征，赛后首发只用于复盘。

### 补充数据

天气使用 Open-Meteo 的赛前预测，并存储抓取时刻、场地坐标和数据归属。天气缺失、场地不确定或许可不适用时不使用该特征。API-Football 仅可作为限额内的二级交叉核验，不保存或公开转发其原始数据。

## 历史审计

审计任务按日期分页获取赛果，再按 `matchId` 获取五玩法奖金历史，生成机器可读的覆盖报告：

- 赛果与 `matchId` 的唯一匹配率；
- 每种玩法的记录覆盖率、奖金结果集合完整率、时间单调性和无效赔率率；
- 让球线变化、取消、延期、更正和重复记录；
- 官方奖金更新时间相对于已知开赛时间的分布。

未通过的比赛只进入隔离清单，不能静默补值或进入训练/验收。数据通过门槛为：赛果匹配率至少 99%，目标玩法在决策时点可用奖金覆盖率至少 95%，且没有未解释的时间倒序或赛后数据泄漏。

## 时间点回测与经济验收

每场比赛先确定真实决策时点：首次为开赛前 120--90 分钟，复核为开赛前 60--35 分钟。每个时点只允许使用 `published_at <= decision_time` 的最后一份完整奖金；成交价使用信号出现后的首个可用官方奖金。最终奖金、开赛后变更和赛果字段均不得进入特征。

训练分割按时间整体切分，不随机拆分：2023--2024 开发；2025 上半年校准及阈值冻结；2025 下半年回顾性锁箱；2026 年初至当前为第二时间外确认集。自动任务上线后的冻结预测和原始快照构成真正的前向金标准集。

五玩法 HAD、HHAD、TTG、CRS、HAFU 分开验收，单场单玩法最多一个候选。候选策略、组合规则、风险阈值和资金规则均需在开锁前冻结。

概率门要求在锁箱上不劣于同一决策时点的官方去水市场概率，并相对市场至少有一个主指标改善 1%；ECE 不高于 0.03（比分可放宽至 0.05），校准斜率在 0.8--1.2。

经济门按官方结算、2 元单位、取消/延期/更正重放和实际取整计算；以比赛日/周为聚类单元 bootstrap。启用门槛为：ROI 95% 置信下界大于 0，赔率恶化 3% 后下界不小于 0、恶化 5% 后点估计不小于 0，最大回撤不超过 10%，且利润不由单一联赛（超过 40%）或最高赔率 5% 的候选（超过 50%）主导。初步有限验证至少 1,000--1,500 个独立候选；正式玩法结论按功效计算，通常至少 3,000--5,000 个候选。比分和半全场预计需要更多样本。

任一玩法失败即保持 `PAPER_ONLY` 或单独关闭，组合盈利不得掩盖失败玩法。

## 异常赔率风险过滤

系统不声称识别或证明“假球”。它只提供可审计的“赔率/数据异常风险”过滤：

- 时间倒序、未来更新时间、比赛身份冲突、赔率不大于 1、玩法不完整、停售后新增变价、快照过期；
- 隐含返还率、单次跳变、跨玩法一致性和方向反转超出开发集预注册阈值；
- 首推至复核期间模型优势缩水超过 50% 时，自动撤销或降为观察。

所有阈值只可在开发集确定；异常过滤必须在独立锁箱中降低损失或回撤，否则删除该过滤器。

## 国内云端试点与通知

Gitee Go 使用私有研究仓库和密文变量，不保存 Webhook、Token 或原始数据。第一阶段仅运行最小探针：请求少量官方接口、验证 JSON 结构与更新时间、记录 HTTP 状态和延迟，并发送不含赔率细节的健康状态。

连续 7 天、每 45 分钟探针的通过标准为：成功率至少 98%，P95 响应小于 10 秒，无地域/WAF 拦截，预计月度构建消耗少于 800 分钟。由于每 45 分钟全天运行在 31 天有 992 次，超过 800 分钟或计费规则不利时自动降至 60 分钟并告警；不得自动付费。未通过则停止该路线，保留本机/低成本国内云作为待选后备，不能假称云端已稳定。

飞书自定义机器人为主通道，发送包含中文赛事、玩法、概率、奖金、风险、建议资金区间、预期奖金区间、状态和网页链接的卡片。个人微信使用 PushPlus 为主、Server 酱为仅重大故障兜底；不模拟操作个人微信客户端，不使用外挂。首次推送只在两个稳定快照后、开赛前 120--90 分钟发出；开赛前 60--35 分钟仅在候选变化、异常或撤销时复核推送。不能覆盖窗口时不补发过期建议。

## 网页与账本

候选页和全部比赛页分离。候选页只展示已经通过玩法/模型门的候选；全部比赛页展示采集完整性与“不推荐原因”。比分、总进球和半全场默认折叠。

账本支持输入预算，展示单关/组合的预计最小、最大及情景奖金；赛果可自动结算后展示当日盈亏、累计盈亏、ROI、资金曲线与最大回撤。页面必须把“研究/模拟”“观察”“已撤销”“数据异常”与“通过候选”显著区分。

## 安全、合规与回滚

项目保持私有、研究定位；不提供自动投注、收款、代购、开户链接或“稳赚”表述。数据接口没有公开 SLA 或批量使用授权时，持续低频使用并准备人工导入；在获得明确许可前不公开原始数据或对外商业化。

所有密钥仅存于本机忽略配置和云端密文变量；已在截图中出现的历史密钥必须保持废弃。任何数据完整性、模型验收、云连通性或通知时效失败，任务失败关闭：保留诊断、停止候选和推送，网页显示数据异常，最后一次有效报告保留只读可追溯版本。

## 交付与验证顺序

1. 实现历史官方赛果、奖金和伤停提供器，以及原始响应追加存档和解析单测。
2. 实现审计报告、隔离清单与数据门；用小样本集成测试验证五玩法映射。
3. 实现决策时点选择、市场去水基线、赔率恶化压力和赛果自动结算；增加无未来数据回归测试。
4. 实现最小 Gitee Go 探针配置、健康状态和飞书/PushPlus测试通知，不迁移正式任务。
5. 报告真实审计结果和回测结果；只有通过数据门和模型门后才改造候选页、全部比赛页与账本，并执行前向纸面跟踪。

## 明确非目标

- 不承诺单场、单日或任意指定周期必然盈利；系统追求的是经独立数据验证、受资金与回撤约束的长期正收益；
- 不自动下单或控制任何博彩客户端；
- 不使用赛后首发、最终奖金或赛果训练赛前模型；
- 不将少量回测样本、命中率或组合盈利当作长期正期望证据；
- 不把异常赔率过滤宣传为“识别假球”。
